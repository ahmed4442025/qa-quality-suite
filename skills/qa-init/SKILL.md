# تهيئة وتحديث بيئة تدقيق الجودة (`/qa-init`)

يدير لوحة المطورين داخل `./qa_dashboard` وتقرير العميل داخل `./qa_report`. افصل دائمًا ملفات الـruntime القابلة للتحديث عن ملفات المشروع التي يجب الحفاظ عليها.

## بنية لوحة المطورين

```text
qa_dashboard/
|-- app/             الواجهة والمنطق وserver.ps1 وrun.bat القابلة للاستبدال
|-- config.js        إعدادات المشروع، حاليًا اسم المشروع
|-- data/            manifest ونتائج الموديولات
|-- modules.md       قائمة موديولات المشروع وحالة فحصها
|-- done.md          معرفات المهام المنجزة
`-- run.bat          launcher توافق ثابت يشغل app/server.ps1
```

لا تضع بيانات المشروع داخل `app/`. لا تستبدل أو تحذف `config.js` أو `data/` أو `modules.md` أو `done.md` أثناء تحديث الـruntime.

## تحديد العملية قبل أي عمل

تحقق أولًا فقط هل `./qa_dashboard` موجود. لا تفحص المشروع، ولا تشغّل `robocopy`، ولا تنسخ أو تحذف ملفات قبل تحديد العملية.

- إذا لم تكن اللوحة موجودة، نفّذ **تهيئة جديدة** مباشرة.
- إذا كانت موجودة وكان المستخدم قد حدد صراحة تحديث التصميم/الـruntime، أو تحديث الموديولات، أو الاثنين، فنفّذ اختياره دون سؤال إضافي.
- إذا كانت موجودة ولم يحدد المستخدم المطلوب، اسأله أولًا أن يختار خيارًا واحدًا:
  1. تحديث ملفات التصميم والمنطق الثابتة.
  2. إعادة فحص وتحديث `modules.md`.
  3. تحديث الاثنين.
  4. إلغاء العملية لأن الأمر شُغّل بالخطأ.
- انتظر الإجابة قبل تشغيل أي مقارنة أو فحص. عند اختيار الإلغاء لا تغيّر أي ملف.

مصطلح **ملفات التصميم** هنا يعني حزمة الـruntime كاملة داخل `qa_dashboard/app/`، بما فيها HTML وCSS وJavaScript والخطوط و`server.ps1` و`run.bat`، وليس المظهر فقط. يبقى `qa_dashboard/run.bat` كـlauncher توافق حتى لا يتغير أمر التشغيل القديم.

## التهيئة الجديدة

1. استخرج اسم المشروع من `pubspec.yaml` ثم `package.json` ثم اسم مجلد المشروع.
2. انسخ قالب `template/qa_dashboard` كاملًا إلى `./qa_dashboard`.
3. استبدل `{{PROJECT_NAME}}` داخل `qa_dashboard/config.js` فقط باسم المشروع، مع كتابة الاسم كسلسلة JavaScript سليمة وآمنة. لا تعدّل `app/index.html` من أجل الاسم.
4. انسخ `template/qa_report` إلى `./qa_report` واستبدل `{{PROJECT_NAME}}` في تقرير العميل كما في القالب الحالي.
5. افحص المشروع وأنشئ `qa_dashboard/modules.md` بالصيغة الموضحة أدناه.
6. أنشئ `qa_dashboard/done.md` فارغًا. لا تستبدله إذا ظهر أثناء إعادة المحاولة.

## تحديث ملفات التصميم والمنطق

لا تنفّذ هذه الخطوات إلا إذا اختار المستخدم تحديث التصميم أو تحديث الاثنين.

### المقارنة قبل التحديث

قارن قالب الـruntime بالمثبت باستخدام `robocopy` في وضع العرض فقط:

```cmd
robocopy "<skill>\template\qa_dashboard\app" ".\qa_dashboard\app" /L /MIR /E /NJH /NJS /NP
```

- Exit code `0`: لا توجد تغييرات.
- Exit codes من `1` إلى `7`: توجد اختلافات قابلة للتحديث.
- Exit code `8` أو أكثر: فشل في المقارنة؛ أوقف تحديث التصميم وبلّغ المستخدم بالخطأ.
- غياب `qa_dashboard/app` يعني أن اللوحة بالهيكل القديم وتحتاج migration، وليس خطأ مقارنة.

إذا كانت الملفات متطابقة، أخبر المستخدم أن الـruntime محدث. عند اختيار التصميم فقط توقف، وعند اختيار الاثنين انتقل إلى تحديث `modules.md`.

### تحديث الهيكل الحالي

عند وجود اختلافات ووجود `qa_dashboard/app`:

- حدّث `qa_dashboard/app` فقط من القالب. يمكن استخدام `robocopy /MIR` لأن الهدف محصور داخل `app` ولا يحتوي بيانات مشروع.
- لا تستخدم `/MIR` مطلقًا على جذر `qa_dashboard`.
- اترك `config.js` و`data/` و`modules.md` و`done.md` دون تغيير.
- أنشئ `run.bat` من القالب فقط إذا كان مفقودًا؛ هو launcher ثابت ولا يحتاج استبدالًا في الهيكل الحالي.

### ترقية الهيكل القديم

إذا كان `qa_dashboard` موجودًا لكن `qa_dashboard/app` غير موجود:

1. لا تحذف جذر الداشبورد.
2. حافظ على `data/` كاملًا، وعلى `modules.md` و`done.md` و`config.js` إن وُجدت، وعلى أي ملفات غير معروفة للمستخدم.
3. إذا لم يوجد `config.js`، استخرج الاسم المعروض من `qa_dashboard/index.html` القديم قبل نقله. إذا تعذر ذلك استخرجه من المشروع، ثم أنشئ `config.js` من القالب.
4. انقل فقط ملفات الـruntime القديمة المعروفة إلى backup مؤقت داخل `qa_dashboard`: `index.html`, `css/`, `js/`, `fonts/`, و`server.ps1`. لا تنقل `data/` أو ملفات التتبع.
5. انسخ `app/` الجديد واستبدل `run.bat` القديم بالـlauncher الجديد.
6. تحقق من وجود `app/index.html`, `app/js/app.js`, `app/server.ps1`, `app/run.bat`, `config.js`, و`data/manifest.js` قبل حذف backup. إذا فشل النسخ، أعد الملفات القديمة من backup.

وجود `<base href="../">` في `app/index.html` يحافظ على توافق ملفات `data/manifest.js` القديمة التي تسجل المسارات بصيغة `data/<module>.js`. لا تعدّل ملفات البيانات لمجرد ترقية الـruntime.

## تحديث `modules.md`

لا تفحص المشروع إلا إذا اختار المستخدم تحديث الموديولات أو تحديث الاثنين، أو أثناء تهيئة جديدة.

افحص `lib/modules/`, `lib/features/`, ملفات Routes وCore وما يعادلها. اكتب أسماء ونطاق الموديولات بالإنجليزية فقط في قائمة مرقمة:

```markdown
# [Project Name] — Project Modules Checklist

1. [ ] Core & Shared — Network (Dio/API), Error Handling, Local Storage & Cache
2. [ ] Authentication — Login, Registration, Password & Session Management
```

عند تحديث ملف موجود، ادمج النتائج بدل استبداله:

- احتفظ بعلامة `[x]` والملاحظات للموديولات التي ما زالت موجودة.
- أضف الموديولات الجديدة بعلامة `[ ]`.
- لا تحذف الموديولات المختفية بصمت؛ ضعها تحت `## Removed / Unmatched` أو وضّحها للمستخدم.
- لا تغيّر `done.md` أو ملفات `data/` أثناء تحديث الموديولات.

## تقرير الانتهاء

اذكر بالضبط ما تم: تهيئة جديدة، تحديث runtime، migration، تحديث modules، أو عدم وجود اختلافات. أكد أن بيانات المشروع و`done.md` حُفظت. أمر التشغيل يظل:

```cmd
.\qa_dashboard\run.bat
```

يمكن فتح تقرير العميل من `qa_report/index.html`، والبدء بفحص موديول عبر `/qa-audit [Module Name]`.
